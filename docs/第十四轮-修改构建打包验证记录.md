## 一、任务背景

第十三轮交付后，用户对网络守护设置页两处文案提出精简需求：

| # | 位置 | 需求 |
|---|------|------|
| 1 | 守护设置 → 自动重连 → 「退避基数」说明 | 移除尾注「（不再翻倍）；防空转由重试上限负责」 |
| 2 | 守护设置 → 检测时机 → 「检测间隔」标题 | 移除「（预设）」括注 |

需求本质：行为变更的缘由属于版本记录（CHANGELOG）的职责，设置页说明无需复述；「（预设）」与下方常驻的「自定义间隔…」入口并存，没有区分作用。保留主体语义：「自愈失败后固定等待 N 秒再重试」「检测间隔」。

## 二、修改过程

### 2.1 定位与考证

全资源目录 grep 确认改动面为 **2 个字符串键 × 5 个语言文件，共 10 处**：

- `guard_cooldown_base_tip`（退避基数说明）
- `guard_interval`（检测间隔标题）

**考证「（预设）」的来源**（判断它是否第十三轮引入，决定是否需要连带处理第十三轮的语义）：

```bash
git show 330bcc6 -- app/src/main/res/values/strings.xml | grep 'guard_interval"'
# 输出为空 → 第十三轮 diff 中没有 guard_interval 行 → 「（预设）」是更早的历史括注
```

结论：直接移除即可。第十三轮新增的「疑似断网检测间隔」自带「跟随检测间隔」档文案，不依赖这个括注做任何区分。

## 三、构建过程

### 3.1 环境预检

构建环境为 4GB 内存沙箱，历史上发生过**两次**构建工具链被系统整体回收（JDK 与 Android SDK 整目录消失、被迫全量重建），因此每轮构建前先做存活检查：

```bash
ls /home/z/jdk/bin/javac            # JDK17（系统 JDK21 是纯 JRE，无 javac）
ls /home/z/android-sdk/platforms/   # android-36
ls /home/z/android-sdk/build-tools/ # 36.0.0
git status --short | wc -l          # 0 —— 工作区干净，改动可控
```

### 3.2 陈旧产物清理

```bash
rm -rf app/build/outputs/apk
```

原因：第十一轮曾踩坑——构建命令超时被杀后 `build/outputs/apk` 里残留**上一轮**的 APK，若不清理会把陈旧产物误当新构建交付（md5 与上轮相同才暴露）。此后每轮构建前必清。

### 3.3 构建约束（4GB 环境防 OOM 惯例）

本环境曾出现多种资源事故，对应约束如下：

| 事故 | 约束 |
|---|---|
| 双 Kotlin daemon + Gradle daemon 三 JVM 并存导致 OOM 被杀 | `-Dkotlin.daemon.jvmargs=-Xmx896m`（命令行覆盖实际生效值）、`org.gradle.jvmargs=-Xmx1536m` |
| 沙箱在工具调用间隔收割后台进程（nohup 秒死、setsid 约 5 分钟被收割） | `--no-daemon` 单次构建；**前台分步执行**不依赖任何后台存活 |
| 单命令 10 分钟超时上限，assembleRelease 约 8.5 分钟逼近上限 | 分三步续跑：compileReleaseKotlin → assembleRelease → assembleDebug，每步独立留存产物与日志 |
| 并行任务内存峰值 | `--max-workers=2` |

### 3.4 构建时间线

| 步骤 | 耗时 | 产物 |
|---|---|---|
| :app:compileReleaseKotlin | 1m04s | 编译通过（资源任务全量重跑，Kotlin 增量） |
| :app:assembleRelease | 8m25s | app-release-unsigned.apk（4,461,737 B，R8 混淆 + lintVital + 资源裁剪） |
| :app:assembleDebug | 1m20s | app-debug.apk（27,731,171 B） |

## 五、验证过程（五层校验）

| 层 | 手段 | 结果 |
|---|---|---|
| 1 源码 | XML 解析 + 残留关键词 grep | 5 文件合法；关键词 0 残留 |
| 2 元数据 | `aapt2 dump badging` | versionCode=6 / versionName=v3.0.0_Alpha-07 |
| 3 资源池 | 解包 APK 内 `resources.arsc` 二进制搜索（UTF-16LE / UTF-8 双编码匹配） | 旧文案 3 处全部 **ABSENT**、新文案 **FOUND** |
| 4 签名 | `apksigner verify --print-certs` | 证书有效且与历史一致 |
| 5 端到端 | 公开 Release 链接下载回比 md5 | release `2723de50…` / debug `8b9d745c…` 与本地构建一致 |

第 3 层的意义：直接对**最终交付的 APK** 的编译后资源池做字符串搜索，验证的是「用户实际下载的包里文案确实已换」，而不只是源码改了。中文在 arsc 中常以 UTF-16LE 存储，故双编码各查一遍。

## 六、发布过程

1. **提交推送**：ecaca8e（6 文件，+12/−10：5 个 strings.xml + CHANGELOG.md），推送 origin/v3.x；
2. **CI 双工作流**（均由 CHANGELOG.md 路径触发）：
   - 「更新 GitHub Pages 上的 CHANGELOG.md」→ success
   - 「构建发行版APK」→ success（CI 自动重建并上传自己的产物，与本地构建字节不同属正常——CI 环境与本地环境构建细节差异）；
3. **资产换回本地构建**：重跑 `release_sync_round14.py`（幂等脚本：PATCH Release 正文取 CHANGELOG 顶段 → 删除 CI 资产 → 上传本地验证过的 APK）；
4. **端到端收口**：公开下载两 APK 与本地 md5 逐一比对一致，第十四轮闭环。

> 为什么坚持把 CI 资产换成本地构建：本地 APK 是经过五层校验（含 arsc 文案比对、签名证书核对）的那一份；CI 产物未做同等深度验证。此为第八轮以来各轮的固定收尾动作。

## 七、遇到的问题与解决

### 问题 1：构建脚本 BUILD SUCCESSFUL 却返回退出码 1

- **现象**：第一步 compileReleaseKotlin 日志明确显示 `BUILD SUCCESSFUL in 1m 4s`，但执行工具返回 exit_code 1，看似构建失败；
- **定位**：脚本开头 `set -e`，尾部有产物展示语句 `ls app/build/outputs/apk/release/ | grep apk$`——在 compile 阶段 apk 目录尚不存在，`ls` 输出为空，`grep` 无匹配返回退出码 1，`set -e` 令脚本立即以非零码退出。**构建本身完全成功**；
- **解决**：探测性的 `ls | grep` 尾部追加 `|| true`（构建成败只以 Gradle 的 BUILD 状态行为准，grep 仅作产物展示不参与成败判定）；
- **复发防护**：修复保存在持久化构建脚本里，后续轮次直接复用，不再踩。

### 问题 2：tag v3.0.0_Alpha-07 指向的提交不是本轮提交

- **现象**：发布收尾核对时，tag 解析到提交 b8eed57，而非本轮 ecaca8e，初看疑似发布错位；
- **查证**：b8eed57 是「重发·第二轮」提交（网络页 BSSID 特权通道兜底）。经核对重发系列历史：自第八轮起，各轮交付只通过 GitHub API 更新 Release **正文与资产**，从未移动 tag——Release 内容始终是最新轮，tag 停留在历史提交位；
- **结论**：既有惯例而非本轮回归。沿用惯例未动 tag：移动 tag 会使已分发的引用失效，且各轮差异已由 Release 正文逐轮完整记录，不依赖 tag 表达版本语义。

### 问题 3：git show 考证时无输出的「假故障」

- **现象**：执行 `git show 330bcc6 -- strings.xml | grep guard_interval` 无任何输出，像是命令失败；
- **解释**：不是故障——无输出恰好证明第十三轮的 diff 中不含 guard_interval 行的任何改动，即「（预设）」早于第十三轮存在。考证命令的空结果本身就是考证结论。
